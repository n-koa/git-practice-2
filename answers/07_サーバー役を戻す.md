# 解答07 サーバー役を戻す

## 手順(server)
### 1〜2. pull してみる
```bash
cd ~/git-practice/server
git status --short
git pull --ff-only
cat compose.staging.yml
git status -sb
```

| コマンド | 意味 |
| --- | --- |
| `git status -sb` | 今のブランチと、GitHub のブランチとの進み・遅れを1行で表示する |

期待結果：
- `git pull` の表示に `+ <英数字>...<英数字> staging -> origin/staging (forced update)` と `Already up to date.` が出る。エラーにはならない
- ファイルの中身は `services:` と `  trivy:` の2行のまま
- `git status -sb` が `## staging...origin/staging [ahead 3]`

### 3〜4. GitHub と同じ状態に戻す
```bash
git reset --hard origin/staging
git log --oneline -3
cat compose.staging.yml
git status -sb
```

| コマンド | 意味 |
| --- | --- |
| `git reset --hard origin/staging` | 今のブランチを、GitHub の `staging`(最後に fetch・pull したときの状態)と同じにする |

期待結果：
- `HEAD is now at <初期状態の commit> 初期状態` と表示される
- ファイルの中身が `services:` の1行
- `git status -sb` が `## staging...origin/staging`(`ahead` が付かない)

## 問いの答え
- A1. `Already up to date.` と表示された。ファイルは戻っていない。エラーにならないので、「戻った」と思い込みやすい
- A2. サーバー役のほうが、GitHub の `staging` より commit が3つ多い(進んでいる)という意味
- A3. pull は、相手にあって自分にない commit を取り込む操作。GitHub が巻き戻ると、GitHub にあるものはすべてサーバー役も持っているので、取り込むものがない。自分のほうが進んでいる分を消すことは、pull の仕事ではない
- A4. 消える。`--hard` は commit していない変更も捨てる。サーバー上に直接書き換えたファイルがないことを、先に `git status --short` で確かめる
